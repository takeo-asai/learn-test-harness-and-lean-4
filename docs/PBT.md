# プロパティベーステスト（PBT）をどう実現したか

結論: [harness/pbt/props.py](../harness/pbt/props.py) は Hypothesis を**ライブラリ**として使う Python スクリプトです。
依存は先頭のコメント（PEP 723 のインラインメタデータ）で宣言しているので、`uv run --script` だけで動きます。
`pyproject.toml` も `requirements.txt` もリポジトリに入れていません。

```bash
uv run --script harness/pbt/props.py          # 全プロパティ
uv run --script harness/pbt/props.py --list   # 何を検査しているかの一覧
```

## 本当はこうしたかった

```bash
uvx some-pbt-tool@1.2.3 kvjson.pbt.yaml
```

テストの中身が仕様ファイルを見れば分かり、ハーネスにはツールのバージョンだけが固定される形です。
**この形は実現できませんでした。** 以下はその理由と、検討した代替案です。

## なぜ宣言的な仕様だけではできないのか

PBT は次の 3 つでできています。

| 要素 | 内容 | 今回の例 |
| --- | --- | --- |
| 生成器 | どんな入力をランダムに作るか | `\` `,` `=` 改行に偏った文字列、文字列→文字列のオブジェクトの配列 |
| 性質 | 入力と出力の間で成り立つべき関係 | `to-json(from-json(J)) == J`、参照モデルとの一致、クラッシュしない |
| シュリンク | 失敗した入力を最小の例まで縮める | Hypothesis が自動で行う |

**性質は任意の計算です。** たとえば今回の性質には次の操作が含まれます。

- CLI を 2 回呼んで合成する
- 出力を JSON の**値として**比べる（バイト列としてではなく）
- 仕様どおりの参照パーサーを持ち、それと比べる
- 「最後のレコードが空でなければ、末尾の改行を省略してよい」という条件を生成器に入れる

これを表すにはプログラミング言語が要ります。だから PBT ツールは
Hypothesis（Python）、fast-check（TS）、QuickCheck（Haskell）、proptest（Rust）のように、
**どれもホスト言語のライブラリ**として作られています。
シュリンクも生成器の内部構造に依存するので、同じ言語の中にあるのが自然です。

PBT という**考え方**は言語に依存しません。言語に依存するのは**ツール**のほうです。
今回のハーネスが言語非依存だというのは、「ハーネスが実装言語（Go）に依存しない」という意味です。
CLI は実行ファイルのパスとしてしか見ていません。
「ハーネスがどの言語でも書かれていない」という意味ではありません。

## 検討した代替案

| 候補 | 何か | 採用しなかった理由 |
| --- | --- | --- |
| `hypothesis` コマンド | Hypothesis 付属の CLI | サブコマンドは `write`（Python のテストコードを生成）、`codemod`（コードの書き換え）、`fuzz`（既存テストの実行）だけ。どれも Python のテストコードが前提 |
| [Schemathesis](https://schemathesis.readthedocs.io/) | Hypothesis ベースの API テストツール | `uvx schemathesis run openapi.yaml` の形でまさに理想どおり動く。ただし **HTTP API 専用**。OpenAPI という標準のスキーマが生成器になり、性質も「500 を返さない」「スキーマに合う」という決まった語彙で足りるから成り立つ。標準入出力の CLI にはそういう標準の仕様書がない |
| [AnySpec](https://github.com/aarongough/any-spec) | 言語非依存のブラックボックス仕様テスト | ランダム生成もシュリンクもない例ベーステスト。言語処理系向け（ソースファイルを処理系に渡す形）で、アサーションは Ruby で書く。2011 年から更新がない |
| npx + fast-check | TS のライブラリ | npx は CLI を実行する仕組みで、ライブラリを `import` するには `package.json` か `node_modules` が要る |
| Deno / Bun | `npm:fast-check` をマニフェストなしで import できる | 実現はできる。ただ、シュリンクと文字列生成は Hypothesis のほうが強く、uv がもう入っていた |
| YAML 駆動の PBT ランナーを自作 | 生成器と性質を決まった語彙で宣言し、それを解釈する小さなツール | 宣言的にできるのは、語彙を決め打ちできる範囲だけ（往復、参照コマンドとの一致、終了コード）。今回は作らないと判断した |
| sh と乱数で自作 | 今の sh + jq ハーネスの延長 | 宣言的にならないうえ、シュリンクもない |
| Go の `testing/quick` や rapid | Go の PBT | 実装と同じ言語になり、外部ハーネスという目的から外れる |

## 採用した形のポイント

- **マニフェストを置かない**: 依存は `props.py` 先頭の `# /// script` ブロックにだけ書く。リポジトリのルートを見て Python のプロジェクトだと誤解されない。
- **ブラックボックスを保つ**: CLI は `$CLI` のパスで渡すだけ。import も内部の検査もしない。
- **参照モデルを持つ**: [docs/SPEC.md](SPEC.md) だけを根拠に書いた小さなパーサー。実装とは独立しているので、差分テストのオラクルになる。
- **ミューテーション計測では乱数を固定する**: `PBT_PROFILE=mutation` で derandomize し、どのミュータントにも同じ入力を当てる。

## 効果（ミューテーションテスト）

例ベースのテストでは生き残った `m14_escape_only_first_comma`（2 個目以降のカンマをエスケープしない）を、
PBT は往復性質と正規形の性質で検出します。結果は README の表を参照してください。
