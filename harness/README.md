# harness/: 外部テストハーネス

`kvjson` を**外から**検査するテスト一式です。
CLI のことは実行ファイルのパス（環境変数 `CLI`）しか知りません。
Go のコードを import することも、内部を覗くこともしません。
したがって、同じ仕様（[docs/SPEC.md](../docs/SPEC.md)）を満たせば、Rust や Python で書き直した CLI もそのまま検査できます。

## 中身

| パス | 種類 | ライブラリ | 何を確かめるか |
| --- | --- | --- | --- |
| [run_tests.sh](run_tests.sh) と [cases/](cases/) | 例ベース・異常系 | **不要**（sh + jq） | 人が選んだ入力ごとに、期待する出力（または拒否）と一致するか |
| [pbt/props.py](pbt/props.py) | プロパティベース（PBT） | Hypothesis | ランダムに作った大量の入力について、入力と出力の**関係**が成り立つか |
| [run_mutation.sh](run_mutation.sh) | ミューテーションテスト | 不要 | 上の 2 つのテストが、わざと入れたバグを検出できるか（テストのテスト） |

```bash
make test       # run_tests.sh
make pbt        # pbt/props.py
make mutation   # run_mutation.sh
```

## なぜ 2 種類あるのか: 「入力→出力を書く」テストと「関係を書く」テスト

### 例ベース（cases/）: 入力と期待値を人が全部書く

`cases/` は「この入力なら、この出力」を 1 件ずつ並べたものです。
**期待値をすべて書いてあるので、ライブラリは要りません。**
CLI に入力を流し、期待値と比べるだけなので、sh と jq で足ります。

- 長所: 「キーの重複はエラー」のように、**狙った境界**を確実に突ける。ケース自体が仕様の具体例として読める。
- 短所: **思いついたものしか試せない**。

### PBT（pbt/）: 入力は機械が作り、期待値は書かない

PBT では入力を 1 件ずつ書きません。
「どんな入力を作るか（生成器）」と「入力と出力の間に成り立つべき関係（性質）」を書きます。たとえば次のような関係です。

- `to-json(from-json(J)) == J`（往復すると元に戻る）
- 参照モデル（仕様から書いた小さなパーサー）と同じ答えを返す

このとき、次の 2 つの理由でライブラリが要ります。

1. **生成器**: 「`\` `,` `=` 改行が多めに出る文字列」「文字列→文字列のオブジェクトの配列」のような、偏りを持たせたランダム生成。
2. **シュリンク**: 失敗した入力を、失敗したまま最小の例まで自動で縮める。ランダムな 30 文字の反例を `"a,b,c"` まで縮めてくれるので、原因が読める。

期待値を書かない代わりに、これらを毎回自分で書くのは大変です。そこで Hypothesis を使います。
Python である理由とほかの選択肢は [docs/PBT.md](../docs/PBT.md) にまとめました。

### 両方要る理由: 実際に、捕まえるバグが違った

[run_mutation.sh](run_mutation.sh) の結果（ルートの README を参照）:

| わざと入れたバグ | 例ベース | PBT |
| --- | --- | --- |
| 2 個目以降のカンマをエスケープしない（m14） | 見逃す | **検出** |
| キーの重複を通してしまう（m05） | **検出** | 見逃す |

- m14 を例ベースが見逃したのは、カンマを 2 個以上含む値を書いていなかったからです。人は思いつかなくても、ランダム生成なら当たります。
- m05 を PBT が見逃したのは、同じ行に同じキーが 2 回並ぶ入力がランダムではほぼ出ないからです。こちらは狙って書いた例が強い。

つまり例ベースは「知っている危険な点」、PBT は「知らない危険な点」の担当です。
例ベースはライブラリなしで書けるので、まずこちらで仕様の要点を押さえ、PBT で網を広げています。

## PBT はランダムなのに flaky ではないのか

PBT は実行のたびに違う入力を試すので、毎回同じバグを検出するとは限りません。
ただし、これは flaky テストとは違います。違いは**失敗が本物かどうか**です。

| | flaky テスト | PBT |
| --- | --- | --- |
| 何が揺れるか | 同じ入力なのに結果が変わる（タイミング、外部サービス、並行性など） | **どの入力を試すか**が変わる。同じ入力なら結果は毎回同じ |
| 正しいコードで失敗するか | する（偽の失敗） | **しない**（性質が正しければ） |
| 失敗したら | 再実行すれば通ることがある。原因を追えない | 反例が表示され、その入力で必ず再現する。本物のバグ |

flaky テストは失敗が信用できません。PBT の失敗は常に信用できます。
揺れるのは「今回はバグに当たらなかった」という**成功の側だけ**です。

### PBT は何をしたいのか: 反例を探す

- 例ベースは**確認**の道具です。人が知っている危険な点を書いておき、壊れていないことを毎回確かめます。
- PBT は**探索**の道具です。人が思いつかなかった入力を機械に探させます。
  同じ入力を毎回試しても新しいことは分からないので、ランダムにします。回すほど、探した範囲が広がります。

このリポジトリでの実例:

- 初回の実行で、対になっていないサロゲート（`"\ud800"`）が往復で壊れることを見つけた。誰も想定していなかった**仕様の穴**で、[docs/SPEC.md](../docs/SPEC.md) に追記した。
- カンマを 2 個含む値で m14 を見つけた。例ベースのケースには、そういう値がなかった。

### 運用での分け方

ランダムな探索を「通らなければマージできない」チェックにすると、既存のバグにたまたま当たった人が止められてしまいます。
そこで、一般には次のように分けます。

| 用途 | 入力 | 失敗したとき |
| --- | --- | --- |
| マージを止めるチェック（CI） | 乱数を固定する。毎回同じ入力なので、例ベースと同じく決定的 | 今回の変更が壊した |
| 探索（手元、夜間ジョブ） | 毎回ランダムで、例数も多め | 新しいバグか仕様の穴を見つけた。反例を `cases/` に移して固定する |

このリポジトリでは:

- `make pbt`: 毎回ランダム（`PBT_PROFILE=default`、200 例）。**探索**用。
- `make mutation`: 乱数を固定（`PBT_PROFILE=mutation`、150 例）。どのミュータントにも同じ入力を当て、実行ごとにスコアが揺れないようにするため。

乱数を固定しても、検出が保証されるわけではありません。毎回同じ結果になるだけです。
たとえば m05 を PBT が見逃すのは、運ではなく、生成器が重複したキーをほとんど作らないからです（正常系の入力は Python の辞書から作るので、キーが構造上重複しない）。

## 各テストの用途（まとめ）

| テスト | 用途 | 毎回同じ結果か |
| --- | --- | --- |
| 例ベース（`cases/`） | 知っている仕様の要点が守られていることを**確認**する | はい |
| PBT（`pbt/`） | 知らない反例を**探索**する。見つかったら例ベースに移して固定する | 探索時はいいえ、乱数を固定すればはい |
| ミューテーション（[run_mutation.sh](run_mutation.sh)） | 上の 2 つが、実際にバグを捕まえられるかを**測る** | はい |
| Lean（[../lean/](../lean/)） | エスケープの規則について、すべての入力で穴がないことを**証明**する | はい |

## 共通のルール

- テスト対象: `CLI=/path/to/kvjson`（コンテナ内の既定は `/opt/impl/kvjson`）
- 「安全に拒否」の判定は両方で同じです: 終了コード 1、標準出力が空、標準エラーにメッセージ、クラッシュなし。
  クラッシュとは、終了コード 128 以上か、標準エラーに `panic:` などが出ることです。
- 出力の比べ方:
  - `to-json` の出力は JSON の**値**として比べます。空白やキーの順序は仕様で自由だからです。
  - `from-json` の出力は**バイト単位**で比べます。正規形が仕様で 1 つに決まっているからです。
